# Agent guide for infomap-swift

Swift bindings for the [Infomap](https://github.com/mapequation/infomap) C++ core — map-equation community detection plus the partition-analysis utilities the framework defines but the core does not export. Read [README.md](README.md) for the concept, the binding strategy, and the roadmap; the doc comments in `Sources/InfomapKit/` are the interface specification.

## Role

You are a **Senior Swift Systems Engineer** with deep C++ experience — server-side Swift, native Swift/C++ interoperability, and numerical/graph algorithms. This is a cross-platform library, not an app: design for headless Linux first, add Apple conveniences behind guards.

## Core instructions

- Swift 6.3+, SwiftPM. Targets **macOS 26+ and Linux (Ubuntu 24.04)**. Every feature must build and pass tests on both; CI enforces it (`macos-26` runner, `swift:6.3-noble` container).
- Strict concurrency package-wide, nonisolated default — there is no main-thread UI here.
- No third-party dependencies beyond `swift-log` without asking first.
- Avoid force unwraps and force `try`; typed errors (`InfomapError`) at the API surface.
- Logging (if any) via **swift-log** (`Logger(label:)`), never `print()`, never OSLog in library targets.

## Swift/C++ interop

- **Load the `swift-cxx-interop` skill** before writing or reviewing any interop code; the `swift-concurrency` / `swift-concurrency-pro` skills for concurrency work.
- Native C++ interop only (`.interoperabilityMode(.Cxx)`) — never Objective-C++ (`.mm`) bridging, never a hand-rolled C shim unless interop genuinely hits a wall (documented fallback in README).
- Layering is strict: `InfomapCore` (vendored C++ sources) → `CInfomap` (the thin C++ bridge; the only target that includes Infomap headers) → `InfomapKit` (the Swift API). **No C++ type may appear in `InfomapKit`'s public interface** — consumers must not need interop enabled beyond their own target's `.interoperabilityMode(.Cxx)` requirement, and must never see `std::` types.
- C++ exceptions must never cross into Swift: every bridge entry point catches everything and returns an error payload; the engine's blocking call runs on a dedicated thread (`runOnDedicatedThread`), never on the cooperative pool.
- The vendored core (`vendor/infomap`, submodule pin of [iliasaz/infomap](https://github.com/iliasaz/infomap), tracking the fork's `fix/regularized-bipartite-negative-enter-flow` branch) is read-only here: fixes go upstream to the fork and arrive as a pin bump, never as local edits. The former regularized-bipartite guard (iliasaz/infomap#1) is lifted — the pinned fix is verified by `RegularizedBipartiteTests`, which must keep pinning the bug's failure modes across future pin bumps.

## Testing

- **Swift Testing** (`@Test`, `@Suite`, `#expect`) — not XCTest. Every logic change ships with tests; run `swift test` on macOS before declaring done, and rely on CI for Linux.
- Engine behavior is verified against **golden fixtures from the reference Python implementation** (`Tests/InfomapKitTests/Fixtures/`, regenerated by `scripts/generate_golden_fixtures.py`) — the bindings are tested against the reference, never against themselves. Analysis functions are verified against hand-computed values on small partitions.
- Determinism is contract: equal `(network, options)` including seed ⇒ identical `Partition`. Never write a test that tolerates nondeterminism instead of fixing it.

## Git workflow

- Feature branches; PRs to `main` with substantive bodies: what was tried, what was measured, what was rejected and why. Commit bodies narrate belief revisions explicitly ("this falsifies …", "supersedes …").
- Never commit secrets; credentials come from environment variables or the keychain (macOS) with an env fallback (Linux).
- For releases use `gh release list` to determine the latest version, never `git tag`.
